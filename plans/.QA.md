# Q&A and Assumptions

## Implementation Assumptions

### ServiceTierSelect Component
- **Assumption**: The `ServiceTierSelect` trigger does not have a `disabled` prop beyond being disabled when no provider is set. This mirrors how `ModelSelect` works (disabled until a provider is selected).
- **Assumption**: When a provider is later cleared (by changing to a different provider in the form), `serviceTier` is also cleared to `''` in the existing provider-change handler. No additional cleanup is needed in `ServiceTierSelect`.

### ServiceTierSelectorModal
- **Assumption**: The clear-selection action inside the modal immediately closes the modal and fires `onSelect('')` — it does not stay open waiting for another confirm step.
- **Assumption**: The preset tier list and the custom input are mutually exclusive: selecting a preset clears the custom input, and typing in the custom input deselects any preset. This mirrors `ModelSelectorModal` behavior.
- **Assumption**: When the modal closes via Cancel, it resets internal state (selected tier and custom value) so reopening shows a fresh modal populated only from `initialValue`.

### Provider Guard Removal
- **Assumption**: Removing the `provider === 'bedrock'` guard is intentional per the plan. Service tiers may be provider-specific in the future, but for now the shared preset list and custom input apply to all providers.
- **Assumption**: The `EditEndpointFormRenderer.test.tsx` test `shows the service tier field only for Bedrock primary models` was NOT modified because it tests the edit-endpoint renderer (which may still conditionally show the service tier field). That test passed without changes, indicating the edit-endpoint form already had its own service-tier rendering logic separate from the inline form renderer.

### Test Strategy
- **Assumption**: Checking `toHaveStyle({ opacity: '0.5' })` on emotion CSS-in-JS components does not work because emotion adds class names, not inline styles. The grey-out test was replaced with checking that the custom input is disabled when a preset is selected (observable via accessible attributes).
- **Assumption**: `Radio.Group`'s `name` prop does not create an ARIA group with that accessible name, so `getByRole('group', { name: /service-tier-selector/i })` fails. Pre-selection tests were refactored to check observable side-effects (confirm button enabled, clear button visible) instead of internal radio state.

### `TrafficSplitModelItem` expansion state
- **Assumption**: When `provider === ''` and `modelName === ''`, the component starts in the expanded state (`isExpanded = true`). Tests for the disabled trigger when no provider is set do NOT call `expandModel` since the item is already expanded.

## Questions

- **Q**: Should the service tier selector eventually show provider-specific preset lists? Currently a single shared list is used for all providers. If Bedrock and OpenAI have different tier structures in the future, `serviceTierOptions.ts` would need a `getServiceTierOptionsForProvider(provider)` function.
- **Q**: Should the `ServiceTierSelect` show the tier value or a human-readable label in the trigger input? Currently it shows the raw value (e.g., `priority`). A label/description mapping could improve UX.
- **Q**: The `EditEndpointFormRenderer` (primary model edit card) was not modified by this plan. Should it also use `ServiceTierSelect` instead of its own rendering? The existing test `shows the service tier field only for Bedrock primary models` suggests it may still be Bedrock-only there.
